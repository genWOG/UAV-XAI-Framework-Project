UAV-XAI / YOLO — СПРАВОЧНИК КОНФИГУРАЦИИ И ЧТЕНИЕ РЕЗУЛЬТАТОВ
=============================================================

1. ГЛАВНОЕ ПРАВИЛО РАБОТЫ С YAML
================================

Начинайте с существующего полного конфига, например config/yolo_multi_method_one_image_fast.yaml, и меняйте только нужные поля. Пример ниже — переопределения основных полей, а не замена всего YAML: в полном профиле должны сохраниться обязательные настройки проекта для модели, задачи, выходов и прочих компонентов.

В репозитории одновременно могут встречаться methods на верхнем уровне и xai.methods. При настройке держите список одинаковым, если код конкретного runner/CLI читает оба поля. Не удаляйте поля из базового YAML только потому, что их нет в кратком примере.

2. ПОЛЯ УРОВНЯ ЭКСПЕРИМЕНТА И МОДЕЛИ
====================================

Параметр — Что делает — Как выбирать
experiment.name — Имя запуска; помогает различать результаты и конфиги. — Давать уникальное и описательное имя, например ship_kernel_960.
image.path — Путь к исследуемому изображению. — Проверить, что путь разрешается из корня репозитория и файл существует.
model.prediction_confidence_threshold — Опциональный порог confidence для этапа получения детекций/поиска target. — Для анализа слабых детекций использовался 0.001. Низкий порог увеличивает количество кандидатов; для штатного сценария оставляйте прежнее поведение, если специальный порог не нужен.
methods — Список методов для pipeline на верхнем уровне, если он используется текущим runner. — Список должен соответствовать xai.methods.
xai.methods — Методы объяснения, которые нужно запускать, например [lime, shap] или все четыре метода. — Для одного методического сравнения задайте только нужные методы: это уменьшает время и упрощает диагностику.
xai.method — Одиночный method selector, используемый некоторыми сценариями совместимости. — Сверяйте с базовым YAML; если он присутствует вместе с xai.methods, не оставляйте случайно конфликтующие значения.
xai.method_configs — Словарь настроек по конкретному методу. — Настройки LIME размещать в lime, SHAP — в shap; не путать num_samples LIME и nsamples SHAP.
output.root — Корневая папка для результатов. — В экспериментах использовалась results. Не коммитьте большие временные каталоги benchmark без необходимости.

Другие обязательные поля model и output оставляйте из базового конфига — полный schema не следует угадывать или заменять кратким примером.

3. НАСТРОЙКИ LIME
=================

Настройки задаются под xai.method_configs.lime.

Параметр — Значение/смысл — Влияние
num_samples — Число perturbations / локальных samples для аппроксимации. — Больше samples обычно повышает статистическую информативность, но пропорционально увеличивает вычисления. Использованы 256 и быстрый профиль 128.
num_segments — Запрошенное число superpixel features. — Больше сегментов даёт более мелкую детализацию, но растит размер локальной задачи и может повышать шум. В основном профиле — 64; ускоренный — 32.
prediction_batch_size — Сколько perturbation images передавать на inference за один пакет. — В оптимизированном коде использован default 32. Увеличение может улучшить throughput ценой памяти; уменьшение снижает пиковую память, но добавляет накладные расходы.
explanation_image_size — Максимальная длина большей стороны рабочего изображения для explanation. — null/отсутствие — исходное разрешение; 960 — основной балансный кандидат; 640 — быстрее, но может ухудшать отдельные метрики/детализацию. Минимально допустимое значение в реализации — 64.
compactness — Параметр сегментации LIME/SLIC. — Более высокие значения сильнее влияют на компактность superpixels. Сохраняйте baseline-значение при сравнительных тестах.
hide_color — Значение, которым заменяются скрытые сегменты; null/отсутствующее значение может запускать режим заливки средним цветом сегмента. — Baseline влияет на ответы модели и на AUC; не менять одновременно с sample budget, если цель — честное сравнение разрешений.

Базовый диагностический совет: при плохом local_fit_score увеличение samples не всегда решит проблему. Проверьте target, segmentation и то, не слишком ли неоднородны perturbations.

4. НАСТРОЙКИ SHAP
=================

Настройки задаются под xai.method_configs.shap.

Параметр — Значение/смысл — Влияние
nsamples — Бюджет оценки SHAP (Kernel SHAP). — Больше samples — дороже и обычно даёт больше вычислительной информации; результат может зависеть от seed. В основных опытах — 256, быстрый профиль имеет меньший бюджет.
num_segments — Число features/superpixels в масочном представлении. — Больше сегментов — больше детализации и дороже перебор коалиций. Основной профиль использовал 32.
prediction_batch_size — Размер батча inference для perturbations. — В оптимизированном коде default — 32. Если память ограничена, уменьшать постепенно, контролируя время.
explanation_image_size — Максимальная длинная сторона изображения, используемого при расчёте attribution. — null — native; 960 — основной балансный кандидат; 640 — latency-профиль. Attribution приводится к размеру исходного изображения для выдачи.
algorithm — kernel либо partition. — kernel — основной вариант для воспроизводимой текущей конфигурации. partition пробовался при 960 px, но полного теста повторяемости нет; пока оставлять experimental.
baseline_mode — Встречающиеся режимы: constant и segment_mean. — Разный baseline меняет perturbations и score/AUC. Для сравнения профилей фиксируйте один режим.
target_iou_threshold — Порог IoU для привязки предсказания к заданной исходной цели, если это поле используется текущим конфигом. — Изменение порога меняет, какие детекции считаются совпадением с target. Не менять одновременно с resolution/sample-budget в контролируемом опыте.
target_score_mode — В текущих вариантах detection объяснения использовалась непрерывная цель confidence × IoU (confidence_iou). — Сохраняет более плавный сигнал при смещении bbox, чем жёсткий нулевой score за непрохождение IoU threshold. Карты, обученные на другой целевой функции, не сравнивать как полностью эквивалентные.

Не все параметры обязаны присутствовать в каждом YAML: при отсутствии применяется default конструктора/factory. Чтобы узнать фактическое значение конкретного запуска, смотрите metadata соответствующего метода в result.json.

5. РЕКОМЕНДУЕМЫЕ ПРОФИЛИ
========================

Основной балансный профиль (для экспериментов)
----------------------------------------------

model:
  prediction_confidence_threshold: 0.001
xai:
  methods: [lime, shap]
  method_configs:
    lime:
      num_samples: 256
      num_segments: 64
      prediction_batch_size: 32
      explanation_image_size: 960
    shap:
      nsamples: 256
      num_segments: 32
      prediction_batch_size: 32
      explanation_image_size: 960
      algorithm: kernel

Это блок переопределений, который нужно объединить с полным базовым YAML, а не отдельный полный конфиг.

Быстрый профиль для интерактивного отладки
------------------------------------------

- LIME: 128 samples / 32 segments.
- SHAP: ориентировочно 128 samples / 24 segments, если соответствующий конфиг проекта использует именно этот профиль.
- Размер explanation: 640 или 960 px в зависимости от допустимого latency.
- После смены бюджета не утверждать, что quality metrics сопоставимы с профилем 256 без повторного измерения.

Что пока не делать default
--------------------------

- Не включать algorithm: partition по умолчанию: было только ограниченное сравнение без repeatability-бенчмарка.
- Не считать 640 px универсально лучше: он быстрее, но отдельные изображения показывали изменения качества.
- Не менять одновременно confidence threshold, target bbox, baseline, сегментацию, samples и resolution — тогда невозможно понять, какое изменение повлияло на результат.

6. КАК ЧИТАТЬ `RESULT.JSON`
===========================

В текущей структуре ищите узел explanations.<method> (например, explanations.lime или explanations.shap). Типовые поля:

Поле — Как трактовать
runtime_ms — Время конкретного explainer. Это не обязательно полный end-to-end latency с загрузкой, детекцией, UI и Gazebo.
metrics.deletion_auc — Площадь под deletion-кривой. При одинаковой процедуре и target меньшая AUC обычно означает, что удаление наиболее важных областей быстрее подавляет score цели.
metrics.insertion_auc — Площадь под insertion-кривой. При одинаковой процедуре большая AUC обычно означает более быстрое восстановление score при добавлении важных областей.
metadata.local_fit_score — Для LIME — насколько локальная аппроксимация соответствует наблюдаемым выходам модели на samples. Высокое значение не означает автоматически хорошую/стабильную визуальную карту; низкое — предупреждение о слабой локальной модели.
metadata.prediction_backend — Путь scoring, реально использованный при построении объяснения; нужен для сверки fast/fallback.
metadata.fast_path_max_score_difference — Максимальная разница score между быстрым и эталонным путём, если это сравнение выполнялось. 0.0 означает совпадение в проверенной выборке, не во всех возможных случаях.
metadata.explanation_image_shape — Размер рабочего изображения для explanation; помогает проверить, применился ли resize.
Другие metadata — Бюджет samples, число сегментов, baseline и сведения о target, если текущий метод их сериализует. При сравнении фиксируйте эти поля.

Если структура result.json отличается в конкретной версии, доверяйте фактическому JSON и текущему коду сериализации; этот документ описывает используемую в последних экспериментах структуру.

7. КАК ЧИТАТЬ CSV СВОДОК
========================

Повторный benchmark создал:

- summary.csv — одна строка на каждый отдельный запуск (variant/image/method/repeat/seed).
- repeatability_by_image.csv — агрегирование повторов для каждой пары variant/image/method.
- summary.json — machine-readable результаты/manifest.
- отдельные логи и per-run YAML внутри каталога benchmark.

Колонки повторяемости:

Колонка — Значение
n_success — Число удачных запусков; должно совпадать с ожидаемым числом повторов.
runtime_median_ms — Медианное время по повторам. Обычно устойчивее среднего к выбросам.
runtime_mean_ms, runtime_stdev_ms — Среднее время и стандартное отклонение latency.
deletion_mean, insertion_mean — Среднее AUC по повторам.
deletion_stdev, insertion_stdev — Разброс quality metrics по повторам; ниже — стабильнее в пределах проверенных seed.

Не агрегируйте все разные изображения в один AUC-рейтинг без контекста target: один и тот же метод может давать существенно разные значения на разных классах и размерах объекта.

8. ПРАВИЛЬНЫЙ ПОРЯДОК АНАЛИЗА ПЛОХИХ РЕЗУЛЬТАТОВ
================================================

1. Посмотрите исходное изображение, класс, confidence и target bbox. Убедитесь, что объясняется нужный объект.
2. Проверьте, не слишком ли низкий порог confidence и не выбрался ли слабый/посторонний кандидат. 0.001 использовался в исследовательских запусках, где важно видеть и слабые детекции.
3. Сверьте explanation_image_shape, budget, число сегментов, baseline, алгоритм SHAP и prediction_backend.
4. Смотрите не только AUC, но и per-step кривые/визуальную карту. Низкий deletion AUC или высокий insertion AUC без проверки target не являются достаточным доказательством.
5. При сравнении профилей фиксируйте seed, target и все настройки, кроме одной исследуемой.
6. Если выбран другой target, другая целевая функция или baseline — объявите это новой экспериментальной серией, а не прямым продолжением старой таблицы.

Ограничение измерений: текущие результаты получены на CPU и пяти тестовых изображениях. Перед использованием с Gazebo нужно отдельно измерить полную latency на целевом устройстве и проверить поведение, когда кадры поступают потоком.
