UAV-XAI / YOLO — РЕАЛИЗОВАННЫЕ МЕТОДЫ, ЭКСПЕРИМЕНТЫ И РЕЗУЛЬТАТЫ
================================================================

1. ОБЛАСТЬ РАБОТЫ
=================

Здесь рассматривается только image-XAI для YOLO detection. В сравнительных запусках использовались четыре метода: Grad-CAM, LIME, SHAP и LRP. Это не benchmark качества детектора на размеченном наборе и не подтверждение требований реального времени на борту: замеры ниже проводились на CPU и на пяти демонстрационных изображениях.

2. ЧТО РЕАЛИЗОВАНО
==================

YOLO fast scorer для LIME/SHAP
------------------------------

- Выделен scorer целевой детекции в src/uav_xai/methods/yolo_fast_scorer.py.
- Быстрый путь пытается использовать Ultralytics predict(..., nms=False) для YOLO-моделей, где доступен NMS-free путь; при невозможности используется fallback.
- В metadata пишется, какой backend реально применён (prediction_backend).
- На текущей локальной модели yolo26n.pt проверено сравнение с базовым scorer для исходного изображения и пяти модификаций: центр закрыт, левая половина закрыта, верхняя половина закрыта, целевой bbox полностью закрыт и изображение размыто. Во всех шести вариантах максимальная разница target score была 0.000000.
- Это хорошая проверка parity для конкретной модели и набора возмущений, но не математическое доказательство эквивалентности на всех изображениях и моделях.

LIME и SHAP: уменьшение вычислительных накладных расходов
---------------------------------------------------------

- Формирование perturbed images в LIME векторизовано вместо многократных вложенных циклов по сегментам и samples.
- Проекция SHAP masks в изображения векторизована; inference организован пакетами.
- Используется configurable prediction_batch_size (в тестовом коде и профилях — 32 по умолчанию для новых быстрых путей).
- Добавлен explanation_image_size: при заданном лимите изображение для расчёта объяснения уменьшается с сохранением пропорций. Attribution затем приводится к исходным размерам.
- Для SHAP добавлен выбор algorithm: kernel | partition.

Выбор confidence порога и профиля
---------------------------------

- Добавлен опциональный model.prediction_confidence_threshold.
- Порог 0.001 использовался в бенчмарках, чтобы не терять низкоуверенные детекции при поиске target. Это увеличивает количество найденных кандидатов и не должно автоматически становиться глобальным production-default.
- Добавлен config/yolo_explanation_resolution960_kernel.yaml как воспроизводимый 960 px / Kernel SHAP профиль.

Тесты
--------

Последний подтверждённый прогон полного набора в локальном рабочем состоянии: 52 passed, 10 warnings за 11.84 s. git diff --check завершился без ошибок пробелов/патча; Git выводил только предупреждения о возможной конвертации LF/CRLF. Эти результаты относятся к локальному состоянию, описанному в карте изменений, и должны быть повторены в фактическом worktree перед отправкой.

7. ПОВТОРЯЕМОСТЬ: ТРИ SEED НА КАЖДОМ ИЗОБРАЖЕНИИ
================================================

Каталог: results/resolution_repeatability_benchmark_20261012_141550.

- Варианты: native Kernel, Kernel/960, Kernel/640.
- Методы: LIME и SHAP.
- Изображения: 5.
- Seed: 2026, 2027, 2028.
- Всего 90/90 запусков успешны: 3 профиля × 5 изображений × 2 метода × 3 повтора.

Медианы времени по пяти per-image медианам:

Вариант — LIME — SHAP — Ускорение относительно native (приблизительно)
Native — 10.839 s — 10.756 s — База сравнения
960 px — 8.087 s — 8.163 s — примерно 25%
640 px — 6.329 s — 6.276 s — примерно 42%

Что показывает разброс
----------------------

- У Kernel SHAP результат зависит от random seed. В варианте 640 px на dog.jpg стандартное отклонение insertion AUC было около 0.159, а deletion AUC на modern_ship.jpg — около 0.164. Это существенная нестабильность на отдельных случаях.
- У варианта 960 px разброс обычно умереннее, но не нулевой: например, стандартное отклонение insertion AUC для dog.jpg было около 0.098, для ship.jpg около 0.070, для test.jpg около 0.107.
- LIME показывал идентичные значения AUC на трёх внешних seed. Это связано с внутренним random_state=42 в объекте LIME: общий seed бенчмарка не менял выбор perturbations для LIME. Поэтому нулевой разброс LIME в этой таблице не является доказательством стабильности к смене seed.
- partition_960 имеет только одиночный сравнительный запуск; стабильность по повторам не проверялась.

8. КАК ИНТЕРПРЕТИРОВАТЬ КАЧЕСТВО
================================

- Deletion AUC: обычно меньше — лучше, если важные области удаляются первыми и оценка исходной цели падает быстро.
- Insertion AUC: обычно больше — лучше, если важные области восстанавливаются первыми и оценка исходной цели растёт быстро.
- Сравнивать можно только при одинаковых target class/box, confidence threshold, baseline, сегментации, порядке perturbations и процедуре подсчёта. Если target или целевая функция изменились, число AUC уже может означать другое.
- Не интерпретировать высокий insertion_auc как доказательство правильности карты сам по себе. Проверяйте также локализацию объекта, исходный confidence, выбранный bbox и стабильность.

Особая осторожность для `ship.jpg`
----------------------------------

При conf=0.001 highest-confidence boat был небольшим bbox примерно [553, 1210, 660, 1307] с confidence около 0.714; другая boat детекция имела крупный bbox [646, 149, 2142, 1390] с confidence около 0.389. Если target берётся как первый/highest-confidence detection, объяснение может относиться к небольшой лодке, а не к большому судну, видимому человеку. До сравнения AUC вручную проверьте target bbox на изображении.

9. ИТОГ ДЛЯ ИНТЕГРАЦИИ
======================

- Для основного экспериментального профиля разумно начинать с 960 px, LIME 256/64, Kernel SHAP 256/32.
- 640 px — профиль минимальной задержки, если допустим компромисс в детализации/стабильности.
- 128 samples подходит для быстрой интерактивной проверки, но метрики нужно читать с учётом более низкого бюджета.
- Partition SHAP оставить experimental, пока не будет хотя бы повторного сравнения.
- Проверка parity fast scorer прошла на шести вариантах одного изображения; расширить её на дополнительные модели/снимки полезно, но не блокировать передачу к Gazebo только ради дальнейших бенчмарков.
- Время выше относится к CPU. Оно не прогнозирует latency Jetson или полный runtime при работе с Gazebo. Требуется отдельный end-to-end smoke test на целевой среде.
